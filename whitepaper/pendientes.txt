## DOBLE CLAVE INSTITUCIONAL + T10

### Concepto
- Cada nodo hijo recibe dos claves independientes:
  K_institucional = institucion_node.grant_key("ruta/del/hijo")
  K_T10 = T10_node.grant_key("institucion.es/ruta/del/hijo")
- La institución es responsable legalmente de la clave institucional
- T10 actúa como verificación independiente adicional

### Jerarquía de prevalencia
- Institucional válida + T10 válida  → confianza máxima
- Institucional válida + T10 inválida → válido con aviso (T10 no reconoce el nodo)
- Institucional inválida + T10 válida → sospechoso
- Ambas inválidas                     → rechazado

### Analogía
- Como un documento con firma del emisor (institucional) y sello notarial (T10)
- El documento es válido con solo la firma — el notario añade verificación independiente

## WALLET COMO GESTOR DE CLAVES UNIVERSAL

### Concepto
- El wallet no es solo identidad — es un gestor de claves para cualquier acción verificable
- Ejemplo bancario:
    bank/santander/user-juan-ruiz/transfer/fields {
        from-account is-type string
        to-account   is-type string
        amount       is-type decimal
        currency     is select-one-from { EUR, USD, GBP }
        concept      is-type string
        date         is-type date
    }
- La transferencia es una acción firmada con respond_to_challenge
- Santander verifica con verify_child_authorship

### Ventaja clave
- El schema es público y estándar
- Dos bancos que implementen el mismo schema son interoperables por construcción
- No requiere acuerdos bilaterales entre bancos — solo adoptar el mismo schema
- Es el argumento de interoperabilidad del whitepaper aplicado a pagos

### Otros casos de uso del wallet como gestor de claves
- Recetas médicas verificables
- Contratos de trabajo
- Reservas verificables (restaurantes, hoteles, vuelos)
- Votaciones verificables
- Acceso a recursos (edificios, sistemas, APIs)

## SISTEMA DE TIPOS — extensión del Style Guide y posible Apéndice G

### string-length y string-pattern como verificadores básicos
- string                        → sin restricción
- string-length:9               → exactamente 9 caracteres
- string-length:8-9             → entre 8 y 9 caracteres
- string-pattern:[0-9]{8}[A-Z]  → regex (más potente)
- dni-es                        → tipo específico con algoritmo completo

### Jerarquía de tipos para documentos de identidad españoles
- string-length:9   → 9 caracteres, sin más verificación
- dni-es            → 8 dígitos + letra calculada (algoritmo módulo 23)
- nie-es            → X/Y/Z + 7 dígitos + letra
- nif-es            → dni-es | nie-es | cif-es  (unión de tipos, notación BNF)

### Tipos numéricos con restricciones
- decimal                    → sin restricción
- decimal-positive           → mayor que cero
- decimal-range:0.01-999999  → rango explícito

### Tipos primitivos verificables por algoritmo (format-verified)
- iban          → algoritmo módulo 97
- dni-es        → letra calculada módulo 23
- cif-es        → dígito de control
- luhn-card     → algoritmo de Luhn (tarjetas de crédito)
- isbn          → dígito de control
- phone-e164    → formato E.164 internacional
- email         → RFC 5322
- url           → RFC 3986

### Gramática formal en notación BNF — candidata a Apéndice G

<type>        ::= <primitive> | <verified> | <composite>

<primitive>   ::= "string" | "decimal" | "integer" | "boolean" | "date"

<verified>    ::= <primitive> "-length:" <integer>
               |  <primitive> "-length:" <integer> "-" <integer>
               |  <primitive> "-pattern:" <regex>
               |  <domain-type>

<domain-type> ::= "iban" | "dni-es" | "nie-es" | "nif-es"
               |  "phone-e164" | "email" | "url"
               |  "isbn" | "luhn-card"

<composite>   ::= "select-one-from" "{" <options> "}"
               |  "select-subset-from" "{" <options> "}"
               |  <type> "|" <type>

<options>     ::= <identifier> | <identifier> "," <options>

<fields>      ::= "fields" "{" <field-list> "}"
<field-list>  ::= <field> | <field> <field-list>
<field>       ::= <identifier> "is-type" <type>
               |  <identifier> "is" <composite>

### Ejemplo completo — transferencia bancaria
bank/santander/user-juan-ruiz/transfer/fields {
    from-account is-type iban
    to-account   is-type iban
    amount       is-type decimal-positive
    currency     is select-one-from { EUR, USD, GBP }
    concept      is-type string
    date         is-type date
}

### Ejemplo completo — registro de usuario
T10/spain/register/fields {
    name             is-type string
    type             is select-one-from { brokenado, verifiado, trusteado }
    dni              is-type nif-es
    email            is-type email
    phone            is-type phone-e164
    signature        is-type boolean
    date             is-type date
}

## SCOPE LEGAL Y RESPONSABILIDAD DE SUBCARPETAS

### Concepto
- Una subcarpeta no solo define identidad sino también contexto de uso válido
  y responsabilidad legal asociada
- El nodo padre declara explícitamente para qué sirve la subcarpeta

### Nuevas propiedades de scope
- [only-valid-for X Y Z]     → uso exclusivo declarado (más fuerte que valid-for)
- [not-valid-for X Y Z]      → usos explícitamente excluidos
- [liability node-url]       → quién asume responsabilidad legal
- [legal-terms url]          → enlace a términos legales machine-readable
- [max-value-per-use EUR:50] → límite de valor por transacción

### Ejemplo completo
uma.es/trusteando/students/brokenado/
├── [only-valid-for events-discounts festivals concerts]/
├── [not-valid-for academic-credentials contracts payments]/
├── [liability uma.es]/
├── [legal-terms uma.es/trusteando/legal/student-brokenado-terms]/
├── [max-value-per-use EUR:50]/
└── [state brokenado]/

### Jerarquía de responsabilidad por nivel
- brokenado → scope mínimo, responsabilidad mínima, max-value bajo
- verifiado  → scope medio, responsabilidad media, contacto verificado
- trusteado  → scope pleno, responsabilidad plena, identidad verificada

### Consecuencia para verificadores
- Un organizador de festival consulta [only-valid-for] antes de aceptar la credencial
- Si el scope no incluye su caso de uso, puede rechazarla aunque sea técnicamente válida
- Es un contrato machine-readable entre emisor y verificadores potenciales

## CORRECCIÓN — only-valid-for vs example-not-valid-for

### Regla
- [only-valid-for] y [not-valid-for] son mutuamente excluyentes — nunca los dos juntos
- [only-valid-for] = scope cerrado, todo lo no declarado queda excluido por definición
- [example-not-valid-for] = scope abierto con exclusiones ilustrativas (no exhaustivas)
- El prefijo "example-" indica que la lista es orientativa, no completa

### Cuándo usar cada uno
- Quiero limitar a casos específicos → [only-valid-for events-discounts festivals]
- Quiero scope abierto pero dar ejemplos de exclusión → [example-not-valid-for contracts payments]
- Ambos en la misma carpeta → ERROR, contradicción no permitida

### Ejemplo corregido
uma.es/trusteando/students/brokenado/
├── [only-valid-for events-discounts festivals concerts]/
├── [liability uma.es]/
├── [legal-terms uma.es/trusteando/legal/student-brokenado-terms]/
├── [max-value-per-use EUR:50]/

## PROPAGACIÓN MONÁDICA DEL NIVEL DE CONFIANZA

### Concepto — analogía con mónadas de Haskell
- brokenado, verifiado, trusteado son contenedores que propagan su nivel
- Una función no puede elevar el nivel de confianza — solo mantenerlo o bajarlo
- El nivel del resultado es el MÍNIMO de todos los niveles de la cadena

### Regla del mínimo
- trusteado(X) → función verifiado → verifiado(resultado)
- trusteado(X) → función brokenado → brokenado(resultado)
- verifiado(X) → función brokenado → brokenado(resultado)
- verifiado(X) → función trusteado → verifiado(resultado)  ← mínimo es verifiado

### Estructura del grafo con niveles
festival/trusteando/attendees/
├── t10/   ← trusteado con firma electrónica (10 letras, nivel más alto)
├── t9/    ← trusteado estándar (9 letras)
├── v9/    ← verifiado (9 letras)
└── b9/    ← brokenado (9 letras)

### Aliases cortos
- t10 = trusteado (10 letras) — nivel más alto, firma electrónica
- t9  = trusteado (9 letras)  — nivel estándar verificado
- v9  = verifiado (9 letras)
- b9  = brokenado (9 letras)

### DUDA DE DISEÑO ABIERTA
- ¿t10 y t9 son niveles distintos o aliases del mismo nivel trusteado?
- Si son distintos: jerarquía completa sería t10 > t9 > v9 > b9
- Si t10 es alias de trusteado con firma electrónica y t9 sin ella,
  entonces son niveles distintos y t10 > t9
- Definir criterio formal para distinguir t10 de t9

### Consecuencia para el grafo
- Un nodo en attendees/b9/ es reconociblemente brokenado sin consultar cada entrada
- El organizador consulta la subcarpeta del nivel que necesita
- La composición de niveles es automática y verificable

## CORRECCIÓN — T10 vs t9/v9/b9

### Distinción definitiva
- T10 = nombre del protocolo y raíz del path (Trusteando, 10 letras)
- t9  = nivel de confianza máximo en la red (trusteado, 9 letras)
- v9  = nivel medio (verifiado, 9 letras)
- b9  = nivel básico (brokenado, 9 letras)

### Jerarquía de confianza
t9 > v9 > b9

### Ejemplos de path
T10/spain/register/t9/user-juan/    ← T10 es raíz, t9 es nivel
T10/spain/register/v9/user-ana/
T10/spain/register/b9/user-dang/

## ROOT SIN DUEÑO — CLAVE ALEATORIA DE ARRANQUE

### Concepto
- El root genera una clave aleatoria de 256 bits al arrancar
- La clave nunca se almacena — desaparece tras derivar las claves réplica
- Nadie, ni el operador, conoce la clave raíz
- Resistente a coerción: no hay nadie a quien presionar

### Proceso de arranque
1. Servidor genera root_key = secrets.token_hex(32)
2. Deriva claves para 3 réplicas: replica_node.grant_key("replica-i-timestamp")
3. Distribuye claves réplica por canal seguro
4. Borra root_key de memoria — desaparece para siempre
5. Cada usuario se registra en las 3 réplicas simultáneamente

### Operación normal (quórum 2 de 3)
- Verificación requiere 2 de 3 réplicas
- Si una réplica cae, las otras dos siguen operando

### Recuperación si cae una réplica
- Las dos réplicas supervivientes tienen quórum
- Generan nueva réplica con clave aleatoria nueva
- Usuarios se re-registran en la nueva réplica
- Las credenciales existentes siguen válidas — no se invalidan
- El sistema vuelve a tener 3 nodos operativos

### Propiedades
- Sin dueño conocido: nadie puede reclamar control del root
- Resistente a coerción: no hay nadie a quien presionar
- Verificable: réplicas se verifican entre sí via quórum
- Antifrágil: si una réplica cae el sistema se recupera solo
- Analogía: Bitcoin — diseñado para funcionar sin depender de su creador

### Pendiente
- Definir el protocolo de re-registro en nueva réplica
- Definir cómo las réplicas supervivientes autentican la nueva réplica
- Incorporar al whitepaper como extensión de sección 4.10 (quórum)
- Implementar en el servidor Cloudflare Worker

## ROOT CON CLAVE ALEATORIA SIN DUEÑO

### Concepto
- El root genera una clave aleatoria de 256 bits en el primer segundo de arranque
- Deriva claves para las réplicas inmediatamente
- La clave raíz desaparece de memoria — nadie la conoce, ni el operador
- Las réplicas son nodos independientes con claves distintas, no copias entre sí

### Proceso de arranque
```python
def bootstrap_root():
    root_key = secrets.token_hex(32)       # clave aleatoria, nunca almacenada
    root_node = TrusteandoNode(root_key)
    
    # Cada réplica recibe clave única — no son copias
    replica_1_key = root_node.grant_key("replica-1")
    replica_2_key = root_node.grant_key("replica-2")
    replica_3_key = root_node.grant_key("replica-3")
    
    del root_key, root_node  # desaparece para siempre
    return [replica_1_key, replica_2_key, replica_3_key]
```

### El usuario recibe tres claves independientes
- Una de cada réplica — distintas entre sí
- Para autenticarse necesita quórum 2 de 3
- Si una réplica cae o es comprometida, las otras dos mantienen la identidad válida
- Un atacante que robe una clave no obtiene las otras dos

### PROBLEMA ABIERTO — control de grant_key tras el arranque
- Si la clave raíz desaparece, ¿quién puede ejecutar grant_key para nuevos usuarios?
- Necesita una función que controle quién recibe claves sin conocer la clave raíz

### Tres opciones

**Opción 1 — réplicas con autoridad delegada**
- Cada réplica puede derivar claves de usuarios dentro de su subárbol
- El root delega grant_key a las réplicas en el arranque
- Más simple pero concentra autoridad en las réplicas

**Opción 2 — quórum de réplicas para aprobar grant_key**
- Usuario solicita clave
- 2 de 3 réplicas verifican requisitos (pago, verificación, etc.)
- Cada réplica otorga su propia clave independientemente
- Usuario recibe 3 claves — una de cada réplica que aprobó
- Más robusto, más coherente con el protocolo

**Opción 3 — función pública auditable**
- Función pública que cualquiera puede auditar
- define criterios: pago verificado, no registrado previamente, cumple requisitos
- Las réplicas ejecutan la misma función y aprueban o rechazan

### Pendiente
- Decidir entre las tres opciones o combinarlas
- Definir cómo se sincronizan las réplicas sobre quién ha recibido clave
  (para evitar que un usuario reciba clave de réplica-1 pero no de réplica-2)
- Relacionar con sección 4.10 del whitepaper (quórum de validación)
- Añadir al whitepaper como variante del modelo de arranque policéntrico

## ARQUITECTURA DE COEXISTENCIA WEB NORMAL + T10

### Concepto
- El servidor web normal y la red T10 comparten el mismo alojamiento
- Misma infraestructura, dos capas con responsabilidades distintas
- No requiere servidor separado ni infraestructura adicional

### Separación de responsabilidades
```
uma.es/              ← web normal, HTML para humanos (sin cambios)
uma.es/trusteando/   ← red T10, carpetas verificables + gestor de claves
```

### Configuración Nginx
```nginx
# Web normal — sin cambios
location / {
    root /var/www/html;
}

# Red T10 — carpetas estáticas + endpoints de claves
location /trusteando/ {
    root /var/www;
    dav_methods PUT;      # append-only, sin DELETE
    autoindex off;
}

# API mínima de claves (Apéndice C del whitepaper)
location /trusteando/_verify   { proxy_pass http://localhost:8080/verify; }
location /trusteando/_challenge { proxy_pass http://localhost:8080/challenge; }
location /trusteando/_grant    { proxy_pass http://localhost:8080/grant; }
```

### Lo que añade una institución para unirse a T10
- Carpeta /trusteando/ con estructura de carpetas
- Script de ~50 líneas que gestiona verify_child_authorship, respond_to_challenge, grant_key
- PUT habilitado, DELETE deshabilitado (append-only)
- Todo lo demás — dominio, servidor, SSL — ya existe

### La idea central (debe estar en la introducción, no en los apéndices)
- La interoperabilidad semántica ha sido el santo grial del intercambio de datos durante 30 años
- Cada intento anterior requirió autoridad centralizada, negociación bilateral,
  o complejidad que impidió la adopción masiva
- Trusteando lo resuelve con una carpeta en un servidor web que ya existe

### Frase clave para la introducción
"Semantic interoperability has been the holy grail of data exchange for 30 years.
Every attempt — EDI, XML schemas, RDF, OWL, API standards — required either
centralised authority, bilateral negotiation, or complexity that prevented mass
adoption. Trusteando's insight is that a folder structure, published on a web
server you already control, under a domain you already own, is sufficient to
achieve interoperability by construction. No negotiation. No integration project.
No shared database. Just a folder."

### Tabla comparativa para el whitepaper
- OWL/RDF → demasiado complejo para adopción masiva
- APIs bilaterales → escala O(n²), cada par negocia
- XML schemas → requiere acuerdo previo entre partes
- Linked Data → separado de la infraestructura existente
- Trusteando → carpetas, cualquiera lo entiende, escala O(n)

### La interfaz desaparece — las carpetas SON la interfaz
- Hoy: app del banco → menús → formularios → sistema propietario
- Con Trusteando: click en bank/santander/user-juan/transfer/
- El wallet lee el schema, sabe qué campos pedir
- El banco verifica con verify_child_authorship
- Mismo click funciona en cualquier banco que implemente el schema

### Generalización a cualquier servicio
- hospital/cita-previa/          → pedir cita médica
- ayuntamiento/padron/           → tramitar empadronamiento
- universidad/matricula/         → matricularse
- seguridad-social/prestacion/   → solicitar prestación
- bank/santander/transfer/       → transferencia bancaria

- PSD2 en Europa lleva años intentando esto con APIs bilaterales y regulación
- Trusteando lo resuelve por construcción — el schema es el contrato
- Sin acuerdos bilaterales, sin integración personalizada

## GRAMÁTICA — CUATRO PATRONES DE DATOS + IDENTIFICADORES ÚNICOS

### Cuatro patrones para expresar datos en el grafo

**Patrón 1 — subcarpeta con nombre**
professors/juan-ruiz/       → el objeto tiene identidad propia en el grafo

**Patrón 2 — [campo:valor] — identificador único**
[client-id:C-123456]/       → dos puntos = identificador único, indexable, clave primaria
[dni:12312312A]/            → ya usado implícitamente con esta convención
[instance:2]/               → idem
[quorum:3]/                 → idem

**Patrón 3 — [campo valor] — atributo simple**
[name "Juan Ruiz"]/         → comillas = string descriptivo, no único
[amount 100]/               → numérico
[currency EUR]/             → enumerado

**Patrón 4 — extern/ — referencia a fuente canónica (como <a href> en HTML)**
extern/bank/santander/accounts/[client-id:C-123456]/
→ referencia a datos que viven en otro nodo
→ evita duplicación e inconsistencia
→ principio DRY aplicado al grafo

**Patrón 5 — fields {} — datos estructurados locales**
transfer/fields {
    from is-type string
    amount is-type decimal-positive
}

### Regla: [campo:valor] elimina necesidad de is-unique
- Los dos puntos llevan la semántica implícita
- El parser sabe por sintaxis qué es identificador y qué es atributo
- No hace falta declarar is-unique en fields {}

### Tabla completa de sintaxis
[campo:valor]       → identificador único, indexable
[campo "valor"]     → atributo string descriptivo
[campo valor]       → atributo numérico o enumerado
extern/ruta/        → referencia externa (link)
fields { }          → datos estructurados locales

### Ejemplo completo — cuenta bancaria
bank/santander/accounts/
└── [client-id:C-123456]/
    ├── [name "Juan Ruiz"]/
    ├── [iban "ES91 2100 0418 00 0200051332"]/
    └── since/2015-03-01/

### Ejemplo completo — transferencia con referencias externas
transfer/
├── [from extern/bank/santander/accounts/[client-id:C-123456]]/
├── [to extern/bank/bbva/accounts/[client-id:B-789012]]/
├── [amount 100]/
└── [currency EUR]/

## OBJETOS VS PROPIEDADES — CONTROL VS DATOS

### Distinción fundamental
- Un OBJETO en una carpeta tiene poder controlador sobre su contenido
  → tiene clave propia derivada por grant_key
  → puede publicar sus propios hijos
  → puede responder retos
  → propaga nivel de confianza
- Una PROPIEDAD es solo un dato del nodo padre
  → no tiene clave propia
  → no controla nada
  → es información firmada por el padre

### Regla de control por sintaxis
subcarpeta-nombre/     → OBJETO — clave propia, controla su subárbol
[campo:valor]/         → PROPIEDAD-ID — dato del padre, sin control
[campo "valor"]/       → PROPIEDAD — dato del padre, sin control
extern/ruta/           → REFERENCIA — apunta a objeto externo, sin control local
fields {}              → DATOS ESTRUCTURADOS — del padre, sin control

### Consecuencia criptográfica
# Objeto → grant_key del padre, puede respond_to_challenge y crear hijos
child_key = parent.grant_key("juan-ruiz")

# Propiedad → no hay clave, solo dato firmado por el padre
# No hay nodo hijo, no hay grant_key

### Consecuencia semántica
- El contexto de la carpeta define qué son los elementos que contiene
- professors/juan-ruiz/ → juan-ruiz ES un objeto-profesor con identidad propia
- transfer/[from:C-123456]/ → C-123456 es una PROPIEDAD de la transferencia
- El mismo identificador puede ser objeto en un contexto y propiedad en otro

### Conexión con propagación monádica
- Un objeto hereda el nivel de confianza de su contenedor y puede propagarlo
- Una propiedad no propaga confianza — es solo información
- professors/b9/juan-ruiz/ → juan-ruiz es objeto con nivel b9
- transfer/[from:C-123456]/ → C-123456 no tiene nivel de confianza propio

### Conexión con UML
- Objeto en carpeta ≈ composición (el padre crea y controla al hijo)
- Propiedad ≈ atributo (dato del objeto padre)
- extern/ ≈ agregación (referencia a objeto con vida independiente)

- Actualizar gramática BNF — distinguir formalmente objeto de propiedad
- Ejemplo canónico: misma entidad como objeto en professors/ 
  y como propiedad en transfer/[from:]

## EFFECTS/ — LA IO MONAD DE TRUSTEANDO

### Separación mundo puro / efectos (inspirado en Haskell IO monad)
- El grafo puro — hechos inmutables, verificables, deterministas
- Los efectos — notificaciones, webhooks, push. Inherentemente impuros.
- on/ es la frontera explícita entre los dos mundos (como on* en HTML/JS)

### Sistema de event handlers on/
group/trusteando/
├── posts/                     ← datos puros
└── on/                        ← event handlers (como onclick, onload en HTML)
    ├── on-new-post/
    │   └── [notify members/]/
    ├── on-new-member/
    │   └── [webhook "https://..."]/
    └── on-member-leave/
        └── [revoke-access posts/]/

### Eventos naturales del protocolo
- on-new-child/      ← se añade un nodo hijo
- on-new-state/      ← nuevo hecho de estado (NO on-state-change — ver abajo)
- on-key-revoked/    ← se revoca una clave
- on-quorum-reached/ ← el quórum aprueba algo
- on-since/          ← llega la fecha de activación
- on-until/          ← llega la fecha de expiración

### DISTINCIÓN CRÍTICA — on-new-state vs on-state-change
- on-state-change → implica variable mutable, rompe append-only ❌
- on-new-state    → reacción a nuevo hecho, compatible con inmutabilidad ✓
- El grafo es append-only — no hay mutación, hay nuevos hechos

## CONDICIONALES — when DECLARATIVO vs if IMPERATIVO

### Distinción fundamental
- [if condition] → imperativo, evaluación en runtime, sale del mundo declarativo
- [when condition] → declarativo, condición como dato, compatible con el grafo

### when en lugar de if
on-new-state/
└── [when state=brokenado]/      ← dato descriptivo, no comando
    └── [action revoke-access]/

## GUARDS LIMITADOS A PROPÓSITO — filosofía Erlang

### Inspiración en Erlang
- Los guards de Erlang son intencionalmente limitados
- Solo comparaciones simples, sin efectos, sin llamadas arbitrarias
- Garantiza terminación, auditabilidad y seguridad

### Predicados permitidos en when (lista cerrada)
[when state=brokenado]/          ← comparación de igualdad
[when level<3]/                  ← comparación numérica
[when since>=2026-01-01]/        ← comparación temporal
[when extern/nodo/exists]/       ← comprobación de existencia
[when quorum-reached]/           ← estado de quórum

### NO permitido en when
[when extern/nodo/_verify]/      ← no llamadas a funciones externas
[when calculate(x+y)>100]/       ← no aritmética arbitraria
[when fetch(url)=true]/          ← no efectos secundarios

### Por qué la limitación es una garantía
- Terminación garantizada — un when siempre evalúa en tiempo finito
- Sin efectos secundarios — evaluar una condición no cambia el grafo
- Auditabilidad — cualquiera puede leer un when y entender cuándo se activa
- Seguridad — no hay inyección de código arbitrario en condiciones

### Conexión con la filosofía general del protocolo
- TrusteandoNode tiene cuatro funciones a propósito
- when tiene un conjunto limitado de predicados a propósito
- La potencia emerge de la composición de primitivas simples
- Igual que Alan Kay con Smalltalk — simplicidad como garantía, no como limitación

## NODOS COMO CARPETAS EJECUTABLES — modelo de ejecución distribuida

### Inspiración en Erlang
- En Erlang los procesos se comunican enviando mensajes: Pid ! {message, data}
- Llamadas a funciones en otros nodos: rpc:call(Node, Module, Function, Args)
- Los guards limitan las condiciones de receive — limitación deliberada

### Equivalente en Trusteando
- El path es la dirección del nodo (como Pid en Erlang)
- Los endpoints _verify, _grant, _challenge son los patrones del receive
- POST uma.es/trusteando/professors/_verify → llamada a función en nodo remoto
- POST uma.es/trusteando/_message → envío de mensaje entre nodos

### Carpeta ejecutable
- Una carpeta con endpoints que responden a mensajes
- El path es la dirección del proceso
- Los endpoints son los patrones del receive
- Modelo: proceso Erlang distribuido sobre HTTP

### Cuándo lo necesitaremos
- Ejemplo end-to-end: hospital referencia datos de universidad
- Transferencia bancaria entre dos bancos distintos
- Cualquier workflow que requiera coordinación entre nodos independientes
- Notificaciones push entre nodos

- Separado del whitepaper core — es una extensión, no el protocolo base
- Desarrollar cuando tengamos ejemplos elaborados que lo exijan

### Relación con el servidor de referencia actual

## TRUSTEANDO COMO WORKFLOW ENGINE DECLARATIVO

### Concepto
- El modelo de carpetas es natural para procesos multi-paso (pipelines)
- plan/ declara los pasos y sus dependencias
- execution/ registra el progreso real
- Cada paso completado está firmado por quien lo completó

### Ejemplo — onboarding de empleado
```
proceso-onboarding-empleado/
├── plan/
│   ├── [state approved]/
│   └── steps/
│       ├── step-1-contrato/
│       │   └── [requires hr/signature]/
│       ├── step-2-alta-seguridad-social/
│       │   └── [requires step-1-contrato/[state completed]]/
│       ├── step-3-acceso-sistemas/
│       │   └── [requires step-2-alta-seguridad-social/[state completed]]/
│       └── step-4-bienvenida/
│           └── [requires step-3-acceso-sistemas/[state completed]]/
└── execution/
    ├── step-1-contrato/[state completed]/since/2026-03-22/
    ├── step-2-alta-seguridad-social/[state completed]/since/2026-03-23/
    └── step-3-acceso-sistemas/     ← en curso
```

### Notificaciones automáticas entre pasos con on/
```
on-new-state/
└── [when step-1-contrato=completed]/
    └── [notify step-2-responsible/]/
```

### Ventajas sobre otros sistemas de pipeline
- Auditable — estado exacto visible en cualquier momento
- Verificable — cada paso firmado por quien lo completó
- Distribuido — cada paso puede estar en un nodo distinto
- Temporal — since/ registra cuándo ocurrió cada paso
- Condicional — [requires] declara dependencias entre pasos
- Sin servidor central — el grafo es el estado

### Casos de uso
- Onboarding de empleados
- Aprobación de préstamos bancarios
- Tramitación administrativa (permisos, licencias)
- Procesos de certificación académica
- Contratos multi-parte con aprobaciones secuenciales
- Procesos de compra con múltiples validaciones

- [requires ruta/[state X]] → dependencia entre pasos
- Añadir al vocabulario reservado (Apéndice A)
- Añadir al Style Guide como patrón de pipeline

## STEPS Y GESTIÓN DE ERRORES EN WORKFLOWS

### Convención steps/ dentro de plan/execution/
- plan/steps/ — pasos declarados en orden
- execution/steps/ — progreso real con estados y fechas
- El orden numérico 01-, 02-, 03- implica secuencialidad sin [requires] explícito
- Un plan alcanza [state completed] cuando todos sus steps están completados
- Eliminar pipeline/ y [requires] como opciones — steps/ es suficiente

### Ciclo de vida de un step
```
[state pending]/      ← todavía no ha empezado
[state in-progress]/  ← en curso
[state completed]/    ← completado con éxito
[state failed]/       ← falló, puede reintentarse
[state aborted]/      ← cancelado, no se reintenta
```

### Ejemplo con fallo y reintento
```
execution/steps/
├── 01-contrato/[state completed]/since/2026-03-22/
├── 02-alta-seguridad-social/
│   ├── [state failed]/since/2026-03-23/      ← queda en historial
│   │   └── [reason "DNI caducado"]/
│   └── [state completed]/since/2026-03-24/   ← reintento exitoso
└── 03-acceso-sistemas/[state pending]/
```

### Reglas
- Si un step tiene [state failed] o [state aborted], los steps siguientes no empiezan
- El historial de fallos se preserva — append-only, nunca se borra
- [state failed] → se puede reintentar publicando nuevo [state completed]
- [state aborted] → cancelación definitiva, no se reintenta
- [reason "texto"]/ → opcional, describe el motivo del fallo
